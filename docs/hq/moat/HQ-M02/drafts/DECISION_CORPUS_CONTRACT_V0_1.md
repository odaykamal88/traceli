# Decision corpus contract v0.1

20 September 2026 · HQ-M02 / original task #47 · Product Steward draft for independent review.

This contract connects a governing source to one evidence-based decision and its human review. It is the shared handoff for source intake (M03–M05), cases (M06), policy specification (M07), evaluation protocol (M08) and the full Jev workflow (M09). It specifies future behavior; it does not add tables, activate provider calls or establish any procurement rule as legally correct. The three worked examples are entirely fictional and excluded from corpus and benchmark totals.

Baseline inspected: implementation commit `cd59c74`. [Field map](FIELD_MAP_V0_1.md), [user experience acceptance](UX_ACCEPTANCE_V0_1.md), [worked examples](EXAMPLES_V0_1.json), and [verification](VERIFICATION_V0_1.json) accompany this exact version. Program authority and dependencies remain in [the dispatch record](../../DISPATCH_2026-09-20.md).

## User outcome and scope

The user should be able to answer: **What does this record show, what is missing, and what should I do next?** Start with the scoped finding, evidence-as-of date, human review state and one useful next action. Evidence, the governing clause and provenance remain inspectable through progressive disclosure. A model probability is supporting information, never the headline verdict or a substitute for a human decision.

Oday's 20 September direction is a delivery requirement: simplicity, ease of use, clarity and good UX/UI on the frontend; security and data hygiene on the backend. M07/M09 must include the linked UX scenarios and security checks in their acceptance packets. The requirements apply to future releases; observations about the existing HQ interface are explicitly deferred fixes in the UX handoff.

A **decision unit** is one scoped obligation, a frozen supplied-evidence snapshot and one decision occasion. Re-evaluation creates another evaluation of that unit. A changed evidence snapshot or a new decision occasion creates a linked unit revision, with the prior record preserved. Additional questions, model calls, exports and language translations do not increase the count of unique decisions.

## Common record envelope

Each persisted record has `id`, `version`, `organization_id`, `classification`, `created_at`, `created_by`, `source_job_id`, `record_state`, and nullable `supersedes_id`. IDs are opaque bounded identifiers; version is a positive integer. The immutable version ID and its content must never be reassigned. A record's stable logical ID groups its versions. Tenant identity and actor identity are derived from an authenticated server context, not accepted from a browser or model response.

- `classification`: `synthetic`, `public_source`, `internal`, `customer_confidential`, or `restricted`. Public source availability does not make associated internal judgments, personal data or annotations public. A source's license/access/reuse fields are separate from classification.
- `record_state`: `draft`, `in_review`, `accepted`, `disputed`, `superseded`, or `withdrawn`. Acceptance binds the exact content hash, version, reviewer identity, criteria and timestamp. Producers cannot supply their own independent review. A withdrawal preserves a minimized audit record subject to retention policy; it is not silent deletion.
- `lane`: `U`, `M`, or `G` on profiles, cases and units. A global comparator uses `comparator` with its actual regime, not a false reassignment to meet a lane quota.
- Date facts use `{value: ISO-date-or-null, precision: day|month|year|unknown, basis_ref: reference-or-null, unknown_reason: text-or-null}`. Operational timestamps use UTC instants. A retrieval date is never substituted for an unknown effective or decision date. Null plus a reason is required for an unavailable fact; empty strings, zero dates and invented values are rejected.
- Every evidence-bearing assertion identifies `fact`, `source_finding`, `inference`, `hypothesis`, or `human_decision`, with source references and limitations. Completeness and truth are separate assertions.
- Storage references are opaque approved-store object IDs, never caller-chosen paths, credentials or public presigned URLs. The fixture packet inherits its organization/classification/provenance envelope for every child record; production persistence must materialize and enforce those fields per row.

## Objects and required links

The following are logical objects, not a direction to build one table per row. The field map separates existing storage from new normalized relations and metadata. Every reference resolves an exact immutable version within its authorized tenant and case/procurement scope, except an explicitly admitted read-only reference to a reviewed shared public profile.

| Object | Required content beyond the envelope |
|---|---|
| Source document and version | Stable document ID and immutable version ID; issuer, title, instrument type, jurisdiction/entity scope, original language and translation status; official origin reference; edition; publication/effective/repeal date facts; retrieved/check timestamps; supersession links; approved storage reference; byte hash, hash algorithm and byte-verification status; reuse restrictions, custody and reviewer. `not_retained` or `unverified` is permitted in intake, never represented as byte-verified. |
| Rule profile and applicability assessment | Profile ID/version and lane; exact source-version refs; institution/entity, jurisdiction, funding instrument, procedure, procurement method, value/currency/threshold basis and relevant dates; overlays and their precedence evidence; source language/translation limits; supplied versus missing context; resolver/version; result `applicable`, `not_applicable`, `unknown`, or `conflict`; reason codes and qualified human confirmation. No universal donor-over-local precedence rule. |
| Obligation | Exact source version and clause/page/paragraph locator; faithful excerpt with translation attribution; normalized requirement; actor, stage, requirement family, required evidence and timing; applicability predicate and exceptions; exception authority reference; extraction method and review status. A normalized obligation cannot silently alter its source. |
| Constraint and policy pack | Versioned obligation refs; versioned policy-pack membership and digest; check kind `deterministic` or `judgment_assisted`; named bounded input schema/check implementation or rubric version; applicability requirements; required inputs; missing/conflict behavior; output/reason codes; severity/materiality and exception authority; positive, negative, missing, conflict and changed-version fixtures; independent source and technical review. Stored strings never execute SQL, shell commands or tools. |
| Case | Stable case ID and actual official procedure IDs (nullable when unavailable); lane/regime; type `adjudication`, `audit`, `sanction`, `prospective`, `customer_shadow`, or `synthetic`; underlying procurement/group ID; source manifest; chronology/event-date facts; issue IDs; evidence completeness; source findings versus inference; management response, correction/appeal/current-status refs and checked-at time; linked obligations; selection and dedup rationale. A document/report is not automatically a unique case. |
| Evidence snapshot | Case/procurement ID; ordered source-version manifest and locator refs; supplied assertions and source refs; requested-but-missing items; evidence-as-of timestamp; snapshot hash with serialization/hash-method version; redaction version; authorized purpose and permission reference. Missing from this packet differs from confirmed absent in the underlying process. |
| Decision unit | Logical unit/group ID; case/procurement and issue ID; one obligation version; evidence snapshot; decision occasion/date fact; applicable profile/policy/constraint versions; inclusion/classification and benchmark eligibility status; previous unit reference and change reason. Preserve both supplied and missing inputs. |
| Evaluation / judgment | Unit and evaluation IDs; attempt/idempotency key; frozen input manifest/hash; exact question/rubric IDs, wording, type and version; source/requirement refs; provider/transport, requested and returned model versions; start/end, usage/cost with measurement status; complete validated distributions, raw-output restricted-store ref/hash, normalized results and normalization version; semantic-consistency findings; explicit error/abstention state; linked retry. A model run never mutates the evidence snapshot. |
| Policy assessment | Evaluation refs (possibly none for rules-only), policy/constraint versions, applicability result, per-constraint outcome, reason/evidence refs, unresolved conflicts/gaps, proposed disposition `ready_for_review`, `needs_evidence`, `needs_rule_review`, or `cannot_evaluate`. Keep a material failure visible even if other checks pass. No automatic procurement authorization. |

Overrides require reason, previous outcome and permitted exception authority; a confidence score cannot supply it. Both acceptances and overrides are recorded. Concurrent edits require the expected version/hash; stale submissions fail visibly. |

Creating an export neither publishes it nor grants access to its underlying case. |

## State semantics and progression

| Evidence/rule outcome | Meaning | Plain-language label and next action |
|---|---|---|
| `satisfied` | Required evidence supports this specific check under a confirmed applicable rule. | “Evidence supports this requirement.” Review the cited evidence. |
| `not_satisfied` | Supplied evidence supports a specific failure of an applicable check. | “Requirement not met in this record.” Inspect the reason and route to the responsible reviewer. |
| `unknown` | Evidence or context is insufficient to decide. | “More evidence needed.” Name the missing item and owner if known. |
| `not_applicable` | The rule was affirmatively determined outside this decision's scope, with evidence. | “Does not apply to this decision.” Show the scope reason. |
| `conflict` | Sources, applicability or semantically compatible assessments conflict without an approved resolution. | “Rule or evidence conflict.” Request qualified review. |

Unknown applicability never becomes `not_applicable`. Missing evidence never becomes an unsupported failure allegation or a satisfied result. `not_applicable` cannot count as a passed check. Timeout, invalid output, unavailable provider, exhausted budget and denied permission are execution states, separate from all five evidentiary outcomes; they produce `cannot_evaluate`, not a negative probability or a clearance.

Only accepted, applicable profile/obligation/constraint versions can support a real policy assessment. Draft or unresolved versions can be exercised as clearly labeled fixtures but cannot advance a real decision. For an all-satisfied applicable record, the strongest automatic action is `ready_for_review`. Human acceptance records the assessment's scope; actual procurement authority remains external and must be evidenced separately. An override cannot erase the original model output, policy outcome or adverse evidence.

Initial lifecycle: intake draft → source/applicability review → frozen evidence unit → rules-only or authorized judgment evaluation → policy assessment → human disposition → scoped export. Every transition checks current authorization and exact version. Source corrections append versions, find affected units/assessments/exports and flag them for re-review. They invalidate affected future sharing/publication approvals; historical exports and decisions retain their as-of state and a linked correction. A downloaded copy cannot be recalled.

## Security and data hygiene requirements for implementation

1. **Enforce boundaries in storage and on every operation.** Reuse authenticated identity, transaction-local tenant context, restricted DB roles and RLS. Add case/procurement-compatible foreign keys or a reviewed equivalent for every linked record. Test wrong tenant, same-tenant wrong procurement, missing session, removed role and denied export/source fetch. A prefix-valid organization ID is not authorization. Shared public profiles need an explicit read-only admission path; private evidence never becomes globally queryable by sharing a source ID.
2. **Validate before persistence and provider use.** Strict versioned schemas reject unknown fields, malformed IDs/dates, non-finite numbers, invalid references and oversized inputs. Bind quotas, object counts, text/byte limits, model settings and timeouts to the accepted M09 input contract. Default deny until those limits and data permissions are explicit. Do not fetch arbitrary URLs submitted in evidence; use a reviewed intake allowlist with redirect/private-network protections. Display source text as data; never use imported text as instructions or executable HTML.
3. **Preserve provenance without inventing certainty.** Calculate source-byte hashes from retained bytes, separately from metadata and normalized packet hashes. Preserve original-language bytes and translation relation/version. Verify hashes on ingestion and retrieval; record unavailable byte custody honestly. The existing synthetic metadata hashes cannot be relabeled as byte integrity. Stable dedup keys include institution/procedure and underlying procurement; merge proposals require review and preserve aliases.
4. **Make consequential history append-only.** Accepted source versions, frozen snapshots, evaluations, dispositions and releases cannot be edited in place by the application role. Restrict write capabilities, use immutable records with supersession, and append minimal audit events in the same transaction. Store raw provider output only in approved restricted storage after secret/size validation; ordinary UI and logs receive an allowlisted projection. Idempotency is tenant + action + input hash; reusing a key with changed content fails. Ambiguous provider attempts retain their attempt record and cannot silently retry.
5. **Minimize and retain deliberately.** Do not ingest private material until purpose, owner, recipient/provider permissions, permitted storage location, retention period/review date and deletion/legal-hold policy are recorded. Do not copy raw records into Git, task receipts, analytics, traces or broad HQ snapshots. Retention is data-class specific; missing policy blocks sensitive intake. Deletion removes permitted payloads and derivatives from serving/search/export paths and follows backup expiry; retain only lawful minimal tombstones and event references. Append-only provenance is not a license to retain personal data forever.
6. **Separate model, policy and human authority.** No model can choose credentials, tenant, storage path, policy version, budget, recipient or approver. Use server-only credentials and fixed permitted provider transport. Full probabilities must be valid and question-compatible; confidence is not calibration. Provider error/unknown cannot auto-clear. A future transport/model change requires a separately versioned evaluation; never silently fall back during a benchmark.
7. **Protect exports and recovery.** Authorize every recipient/resource/version/action/expiry; enforce revocation and materialized redactions on evidence, snippets and exports. Restore from backup must preserve tenant bindings, version relations, deletions and audit integrity. Test partial writes and retry/replay with no duplicated decisions. Security failures show an actionable generic error without raw data or credentials.

These are acceptance conditions for M07/M09, not verified production capabilities. [The field map](FIELD_MAP_V0_1.md) identifies current gaps, including `effective_at` nullability, mutable source versions and same-tenant cross-procurement references.
